# Research Methodology

## Dataset / Source

Synthetic, controlled cloud-security configuration and access-request
data, created specifically for this project. All users, roles,
resources, VPCs, and policies are seeded rows in a local SQLite database
(`backend/app/services/seed_service.py`) - no real identity, cloud
account, credential, or network is used or represented. Access-request
data is generated by explicitly submitting requests to the running API,
either through the Attack Simulator, direct API calls, or the automated
test suite - never sampled or inferred from a real system.

## Method

Rule-based contextual authorization simulation. Every request is
evaluated by five independent, deterministic engines (IAM, VPC, resource
policy, MFA, risk), each implemented as a pure function over explicit
inputs, combined by a single central decision engine. No machine
learning, statistical inference, or external service is involved in any
decision.

## Variables

Drawn directly from the implementation
(`backend/app/schemas/access.py::AccessRequestIn` and the engines that
consume them):

| Variable | Source |
|---|---|
| IAM permission | The requesting user's role and its granted action/resource-pattern permissions (`permissions` table). |
| Source VPC | The `source_vpc` field of the request, matched against the resource's active policy's trusted VPC (`policies.trusted_vpc_id`). |
| Resource classification | The `classification` field of the requested `resources` row (`PUBLIC`, `INTERNAL`, `CONFIDENTIAL`, `RESTRICTED`). |
| MFA | The `mfa` boolean field of the request, checked against the resource's active policy's `mfa_required`. |
| Request type | The `request_type` field (`NORMAL`, `SUSPICIOUS`, `AUTOMATED`, `UNKNOWN`). |
| Repeated failures | The count of the same user's denied requests in the preceding 15 minutes, computed from the `access_requests` table. |
| Policy configuration | The resource's active `policies` row: required role, trusted VPC, MFA requirement, maximum risk score, external-access setting, enabled state - all administrator-editable at runtime. |

## Primary Outcome

`ALLOW` or `DENY`, produced exclusively by
`backend/app/engine/decision_engine.py::decide`.

## Secondary Outcomes

- **Risk level** (`LOW` / `MEDIUM` / `HIGH` / `CRITICAL`), from the risk
  engine.
- **Security event**, created for every denied request and every applied
  policy change.
- **Alert**, created for any request (allowed or denied) assessed as
  `HIGH` or `CRITICAL` risk.

## Validation Approach

Two complementary methods were used throughout the project:

1. **Automated testing** - 82 `pytest` tests exercising the real API
   (via FastAPI's `TestClient`) and, for the risk and decision engines,
   direct unit-level calls to the pure engine functions, against the
   project's real database.
2. **Live demonstration** - the same scenarios re-executed against a
   running `uvicorn` server and a running React frontend, with results
   independently cross-checked against the automated test results and
   the raw API JSON.

## Explicit Scope Statement

This is a controlled, local, academic simulation. It is not a production
AWS deployment, does not connect to any real cloud service, and does not
use any real credential. All findings in
[`RESULTS.md`](RESULTS.md) describe the behavior of this simulation
only.
